What you've actually inherited

Nine tools — eight in real use, plus adoption-tracker, which was built and never turned on. All of them are Google Sheets + Google Apps Script (Google's built-in scripting). There is no server, no hosting bill, and nothing to install. Each tool is a Google Sheet with code attached; some also publish a web page. If you can edit a spreadsheet, you can keep every one of these running — the day-to-day settings all live in sheet tabs, not in code.

You do not need to be able to write code to own this. You need to be able to: open a Sheet, open Extensions → Apps Script, pick a function name from a dropdown, and press Run. That's the whole skill set for everything in this guide.
Every tool card has a collapsed Go deeper panel written for a developer — JSON, hash maps, edge cases. You can ignore all of them for the rest of your life and still keep every tool running. They're there for whoever you hand this to next, or for the AI you point at a problem — not a prerequisite for you.

The one screen you'll keep coming back to

Almost every instruction in this guide sends you to the Apps Script editor. You reach it from any tool's Sheet: Extensions → Apps Script. It opens in a new tab and looks like a code editor — intimidating the first time, but you only ever touch five things on it. Here's the whole map:

The file list (left)
The .gs and .html files that make up the tool. You rarely edit these by hand — you paste whole files in when updating code.
The function dropdown (top)
A menu next to the ▶ Run and 🐞 Debug buttons. This is where you pick a function by name — e.g. initializeSheet — before running it. When a card says "run X," this is where.
▶ Run
Runs whatever function is showing in the dropdown. The first time, Google asks for permissions — always "Select all." Output and errors show in the Execution log that slides up at the bottom.
🕐 Triggers (left rail, clock icon)
The list of scheduled jobs. This is "the Triggers page" every card refers to. Empty here after a copy = the tool's automation is off. You add or delete rows here.
⚙ Project Settings (left rail, gear)
Where Script Properties live — the hidden IDs and tokens two tools need re-typed. Scroll to the bottom of this screen to find them.
Deploy (top-right, blue)
Only for web-app tools. Deploy → Manage deployments → Edit → New version is the exact path that pushes a code change live. A plain save does not go live until you do this.
If you can find those six things, you can do everything in this guide. Nothing else on that screen matters for day-to-day ownership. When in doubt, take a screenshot of what you're seeing and ask the AI (see 🤖 Editing with AI) "where is X on this screen?"

If you do nothing else, do these six

⚠ There are two copies of every tool — and they are not the same

Each tool exists twice: as files in the GitHub repo (the written-down version, which is what the deep dives on this page describe) and as the live Apps Script project attached to the real Sheet (the version that actually runs). Nothing syncs them. Updating a tool means opening its Apps Script project and pasting the new code in by hand, then publishing a new version.

So the live code can lag the repo — and as of the date in the footer, it does. Fixes and features for catering-quote-tool, Monday Morning Huddle and payroll-system were written and committed but never pasted into the live projects. If a card here describes something you can't find in the running tool, this is why — it isn't broken, it was never deployed.
How to tell what you're actually looking at: open the tool's Apps Script editor and read the code there. That is the truth. The repo is the backup and the history; this guide is the explanation. When they disagree, the editor wins.

🩺 Monthly pulse check

Everything here fails silently. The rest of this guide tells you how to fix a tool after it breaks; this card tells you how to catch it breaking. Ten minutes, once a month, on a calendar reminder. This is the single highest-value habit for a hub of tools that never announce their own failures.

The ten-minute sweep — your monthly pulse check

  1. Did the emails actually arrive? You are subscribed to (or CC'd on) the weekly summaries. If a Monday came and no payroll summary, no huddle report, no waste summary landed — that's the signal. A missing email is the only outward sign most of these tools give.
  2. Spot-check one tool's Triggers page. Rotate through them — open one tool's Apps Script editor, click the 🕐 clock icon, confirm the expected rows are there and none say "failed." Payroll should show 3, schedule-counter 3, training-tracker 5, catering 5+. An empty or shrinking list is a dead tool that still looks fine.
  3. Open the two customer-facing web apps. Load the catering ?view=app page and the guest-recovery form. If either shows an error or a blank page instead of loading, a deployment or permission lapsed.
  4. Glance at the catering Supplies "no recipe" list. If it's growing, the menu drifted from Recipe_BOM — nothing is broken, but the numbers are quietly going stale.
  5. Confirm the ownership + contacts tables are still true. Someone left? A tool moved drives? A new /exec URL? Update the tables in Wiring & ownership now, while you remember, and re-export.
If all five are clean, you're done — close the tab. If one isn't, it points you straight at the matching 🚨 Something's broken card. Finding it here, in ten minutes, is the difference between "I noticed the report was late" and "payroll hasn't backed up in two months."

🚨 Something's broken?

Find the symptom, get the cause and the exact fix. This is the section to reach for first.

Master revival sequence

What to do, in order, to bring any tool back to life on a new account. A copy carries the tabs and settings — nothing else.
  1. Ownership. Make sure the script and its Sheet live on an org drive (store or leadership), not a personal account. Owning the file is what lets you redeploy.
  2. Setup. Open the Apps Script editor, run the tool's Setup function (see its card). Grant permissions when asked. Every setup function in this hub is safe to run more than once.
  3. Re-seed Properties. Only two tools need this — schedule-counter and guest-recovery. Skip otherwise.
  4. Enable automation. Run the tool's trigger-setup function. Separate step for every tool except payroll — without it, nothing is scheduled and the tool silently does nothing. Two exceptions to read on the card itself: training-tracker also needs two form-submit triggers added by hand, and catering has five installers plus one nightly trigger you make yourself.
  5. Deploy (web apps only). Deploy → New deployment → Web app → set Execute as + Who has access → copy the new /exec URL → update any links that used the old one.
  6. Re-authorize. Run a function that touches Drive/Calendar and grant every scope — Google's consent screen lets you skip Drive silently. Always “Select all.”
  7. Verify. Don't stop at "no errors." Each tool card has a Verify line — do that thing and see the result. Most of these tools fail silently, so "it didn't error" proves nothing.
Execute-as ≠ file owner. An org-owned script still runs as whoever deployed it, until a successor cuts a new deployment as themselves. Org-owned files make that a 2-minute fix; personal-account files make it impossible.
The single most common mistake: doing steps 1–3 and stopping. The tool opens, looks perfectly healthy, and quietly never sends another email. Step 4 is not optional.

🤖 Editing these tools with AI (a crash course)

These tools were built by describing what was needed in plain English to an AI assistant, which wrote the code. You can maintain and extend them the same way — you do not need to learn to code, you need to learn to direct the coding. This is the whole method, the models, the costs, and the guardrails.

What "vibe coding" actually is

You describe the change you want in normal words. The AI writes or edits the code. You paste that code into the Apps Script editor, run it, and see if it worked. If it didn't, you tell the AI what happened and it tries again. That loop — describe → paste → run → report back — is the entire skill. The AI is fluent in Google Apps Script; you are fluent in what the restaurant needs. That division of labor is why a non-programmer built this hub.

The AI cannot see your Sheet, cannot open your Apps Script editor, and cannot run anything for you. It only reads what you paste in and writes text back. You are the hands; it is the head. Every "run this / paste that / here's the error" step is yours.

What to use

Any capable AI chat assistant works; this hub was built with Claude (by Anthropic), so these tools "think" in the same style Claude writes. Three ways to reach it, simplest first:

  • claude.ai in a browser — the simplest. Paste a file in, describe the change, copy the answer back into Apps Script. No install. Start here.
  • The Claude desktop or mobile app — same thing, nicer for going back and forth and for attaching screenshots of an error.
  • Claude Code — a power-user tool that can read a whole project folder at once. This is what the tools were originally built with. Overkill for a small fix; worth learning if you end up doing this a lot.
Other assistants (ChatGPT, Gemini, Cursor, GitHub Copilot) can do this too — the method is identical, only the website changes. Pick one and get comfortable; don't shop around mid-task.

Which model, and what it costs

"Model" = which version of the AI's brain you're using. Smarter models cost more and think a little slower. For editing real code, use the most capable model you have access to — a bad edit to payroll costs far more than a few cents of AI time. Save the cheap, fast models for quick questions.

Give the AI the context it needs — the folder Brent left

The AI starts every conversation knowing nothing about your restaurant, your tools, or how they're wired. It's brilliant but amnesiac. The single biggest thing that makes it useful is pasting in the right context first. Before you leave, Brent is putting a context folder on the leadership Drive holding exactly this material — use it.

For any change to one tool, give the AI:

  • That tool's GUIDE.md from the repo (or its Go deeper panel here) — the plain-language explanation of how it works.
  • The actual .gs / .html file you want changed — copy it out of the Apps Script editor and paste the whole thing.
  • This guide's warnings — the copy-loses-triggers rule, the "publish a new version" rule, the gotchas on the tool's card. Paste the relevant bits so the AI doesn't reinvent a trap you already know about.
A good opening move: "Here is a Google Apps Script tool and its guide. [paste both] I want to [change]. Don't rewrite anything I didn't ask about. Show me exactly which file to change and what to paste, and tell me what to run and re-deploy afterward." The more you front-load, the less it guesses.

The safe way to make a change

  1. Back up first. For a Sheet-plus-code tool, File → Make a copy. For code, keep the old version pasted in a doc. You want a way back.
  2. Never test on the live payroll or a customer-facing tool. Make the copy from step 1 your sandbox. Break things there, not in production.
  3. Describe the change to the AI with the context above. Ask for the whole changed file, not a fragment — pasting a fragment into the wrong spot is the #1 beginner mistake.
  4. Paste it in, run the setup function, test it on the sandbox. Use the tool's Verify line from its card — don't trust "no error."
  5. Only then move it to the real tool, and for a web app, Deploy → Manage deployments → Edit → New version or the change never goes live.
  6. Update this guide. If you changed how a tool works, edit its card (the TOOLS array in Guide.html) so the next person isn't reading fiction.
When something errors, copy the exact red error text (or screenshot it) and paste it straight back to the AI. "It says TypeError: cannot read property 'getRange' of null" gets a real fix; "it's broken" gets a guess.

Rules that keep you out of trouble

  • The AI is confident even when it's wrong. It can invent a function name or a Sheet tab that doesn't exist. If it references something you can't find, say so — don't assume you missed it.
  • It doesn't know today's state. It can't see that a trigger is missing or a property is unset. You report what you see; it reasons from that.
  • Never paste secrets into it that you wouldn't want stored elsewhere — real apiToken values, and be thoughtful with sheet IDs. Ask about the shape of the fix, then fill the real secret in yourself in Script Properties.
  • Small steps beat big ones. One change, test, next change. A giant "rewrite the whole thing" answer is hard to check and easy to get subtly wrong.
  • If you're in over your head, stop and call a human. The contacts table exists for exactly this. AI is a force multiplier, not a substitute for the person who built it.

Retiring a tool

If you inherit something you don't want, turn it off properly — a half-dead tool still emails people.
  1. Delete its triggers first. Apps Script editor → Triggers (clock icon) → delete every row. Most tools also have a remove…Trigger() function. Until you do this, it keeps emailing on schedule with nobody watching.
  2. Archive the deployment. Deploy → Manage deployments → Archive. Anyone holding the old /exec link then gets an error instead of a silently stale tool.
  3. Tell whoever POSTs to it. Only guest-recovery-log has an external poster, but check before assuming.
  4. Keep the Sheet. Don't delete data — rename it ARCHIVED — <name> and move it to an archive folder. Storage is free; a deleted payroll history is not recoverable.
  5. Note it here. Add it to the excluded list in the footer so the next person doesn't try to revive it. manager-hub is the existing example.
  6. Delete its card. Remove its object from the TOOLS array in Guide.html and redeploy — the tables rebuild themselves. A retired tool left on this page is a successor's wasted afternoon.
There is one live candidate right now: adoption-tracker was never wired up, so retiring it costs nothing — there are no triggers to delete and no deployment to archive. Just decide, and take it off this page.
A tool with triggers still installed but nobody maintaining it is worse than a deleted one — it sends stale numbers to real people who assume someone checked them.

Glossary

Every term in this guide, in plain language. No prior knowledge assumed.
Apps Script
Google's built-in programming tool. Reach it from a Sheet via Extensions → Apps Script. It's where the code lives and where you press Run.
Function
A named action in the code, e.g. initializeSheet. You run one by picking it from the dropdown at the top of the editor and clicking ▶ Run.
Setup function
The one you run once to build a tool's tabs and settings. All of them here are safe to re-run — they create what's missing and leave your data alone.
Trigger
A scheduled job — "run this every day at 3pm." Triggers never survive a copy, which is why re-installing them is its own revival step.
Deployment
Publishing a script as a web page. Produces the /exec URL. Code changes do not go live until you publish a new version.
/exec URL
The public web address of a deployed tool. Pasted into emails and bookmarks — so it changing quietly breaks things elsewhere.
Execute as
Whose Google account the tool acts as when it runs — whose Drive it writes to, whose Gmail it sends from. Set at deployment, not by who owns the file.
Who has access
Who's allowed to open the web app. "Anyone" means no sign-in (needed for outside guests); "Anyone within the organization" means a work sign-in is required.
Scope / permission
What Google services the script may touch — Drive, Calendar, Gmail. Granted on the consent screen. Always choose "Select all."
Script Property
A hidden setting stored with the script rather than in a sheet tab — used for IDs and tokens. Never survives a copy; must be re-typed.
Sheet ID
The long code in a Sheet's URL between /d/ and /edit. How one tool finds another.
Idempotent
Safe to run repeatedly with the same result. Every setup function here is.
Menu tool
A tool with no web page — you use it from a custom menu that appears in the Sheet's toolbar when you open it.
Standalone script
A script not attached to any Sheet; it finds its Sheet by an ID written in the code. Only guest-recovery-log works this way.
Form-submit trigger
A trigger that fires when someone submits a linked Google Form, rather than at a set time. Training-tracker runs on two of these, and no setup function installs them — you add them by hand on the Triggers page.
Repo / GitHub
The public folder of source code every tool is copied from — github.com/brentb154/Brent-Chick-fil-A-Tech-Projects. Read-only reference. It is not connected to the live tools; nothing syncs.
Token
A password-like string a site sends along with data so the tool knows the request is legitimate. Only guest-recovery-log uses one (apiToken).
app_cache
A hidden tab in schedule-counter holding one big pre-computed blob of text, so the page loads instantly instead of recalculating. Never edit it by hand — it rebuilds itself every Monday.
PO
Purchase order — the number a school or church gives you so they can pay later. Catering chases missing ones automatically.
DISD
Dallas ISD. Catering sends them their own weekly recap, on its own trigger.
CH / DBU
The two restaurants (Cockrell Hill and DBU). They appear as tab-name prefixes — CH Menu, DBU Menu — and are renameable in catering's Settings tab.
Recipe_BOM / BOM
Bill of materials — the tab listing what components each menu item is made of, so the Supplies tab can turn "40 nugget trays" into cases of product.
Silent failure
The default failure mode of nearly everything here: the tool opens, shows no error, and quietly stops doing its job. Why every card has a Verify line.
